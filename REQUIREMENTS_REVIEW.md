# ПИС 2026: разбор требований перед реализацией

Дата: 16 октября 2026 года.

Основание: памятка и описание преподавателя, локальный репозиторий `../pi_24_2026_students`, файл [domains.docx](domains.docx). Материалы Google Drive не анализировались; выводы относятся к предоставленному тексту и локальным файлам. Это разбор требований, а не готовая система проверки. Предложения ниже требуют согласования и не являются объявленными студентам правилами.

## Что уже определено

- Работа командами по 2–3 человека, один GitHub-репозиторий на команду, одна выбранная тема.
- Преподаватель ведёт лабораторные и сроки в отдельном Markdown-файле; команды, репозитории и номера тем — в другом.
- Пять диаграмм в корне: `use_case.md`, `er.md`, `system_sequence.md`, `class_sequence.md`, `classes.md`. В каждом файле ровно один блок Mermaid и текстовое описание.
- Код приложения находится в `solution/`, видео — в `report/`, описание проекта, участники и запуск — в `README.md`.
- Утренний запуск: синхронизация репозиториев → проверка через подпроцесс Codex → сохранение замечаний → сбор сводной таблицы.
- Оценки за лабораторную: 0 грубых ошибок — 5, одна — 4, две — 3. Просрочка больше трёх дней снижает оценку на один балл.
- Автомат — среднее по лабораторным с округлением вниз. Окончательное решение принимает преподаватель.

## Что действительно делает прежний репозиторий

| Участок | Найденное поведение | Что означает для ПИС |
| --- | --- | --- |
| `run_check.sh` | Последовательно запускает синхронизацию и проверку | Общую последовательность можно сохранить; расписания и публикации в этом файле нет |
| `scripts/sync_students.py` | Читает `students.md`, удаляет весь локальный `tmp/`, заново клонирует с `--depth 1` | Для времени изменения отдельной лабораторной нужна история, которой в таком клоне нет |
| `scripts/check_diagrams.py`, `call_llm` | Вызывает HTTP API шлюза; модель по умолчанию `claude-sonnet-ccr` | Подпроцесс Codex — новая интеграция, прямого готового аналога здесь нет |
| `SYSTEM_PROMPT`, `build_user_message` | Проверяет только `classDiagram`; передаёт задание, UML-памятку и извлечённый блок | Нужны критерии для пяти видов работ, тема команды и пояснения из Markdown |
| `extract_mermaid` | Регулярным выражением извлекает первый блок | Не проверяет ровно один блок и не выполняет полноценную проверку синтаксиса Mermaid |
| Кеш проверки | Один SHA последнего коммита на весь репозиторий | Любое изменение запускает все работы; изменение критериев само по себе повторную проверку не вызывает |
| Обработка исключений в `main` | Пишет ошибку проверки в файл результата и затем сохраняет SHA как проверенный | Техническая ошибка может попасть в категорию грубых ошибок и не повториться при следующем запуске |
| Отсутствующий файл | Проверка пропускается без записи нового результата | После удаления диаграммы старый результат может сохраниться |
| `update_results_md` | Защищает ранее зачтённую ячейку от понижения | Нужно явно выбрать правило сохранения оценок после исправлений и регрессий |
| Ручная оценка в `students.md` | Отключает проверку студента и скрывает результаты отдельных работ | Для ПИС полезнее отдельные ручные решения по лабораторным с причиной |
| Проверка сходства | Модель сравнивает с уже проверенными работами; `PLAGIAT` классифицируется как подозрение | Это отдельное незаказанное пока правило; нельзя автоматически переносить санкции из старого README |

В старых сохранённых результатах есть пример проблемы подсчёта ошибок: `results/bulatov_ilya/sboi.md` содержит нумерованные пункты с фразой «Ошибки нет». Поэтому считать грубые ошибки по числу пунктов ответа нельзя. Заголовок старого скрипта также упоминает эталонный код, но фактический `build_user_message` его не передаёт. Поведение нужно переносить по коду, а не по описаниям.

## Решения, без которых нельзя однозначно выставлять оценки

### 1. Полная шкала и несданные работы

Не определены оценка за три и более грубые ошибки, отсутствие файла, пустую работу, неверный формат и работу на другую тему. Не определено, является ли синтаксически сломанная диаграмма одной ошибкой или основанием не оценивать содержание.

Предложение: различать «не сдано», «не проверено», «технический сбой», «проверено» и «подтверждено преподавателем». Для проверяемой работы можно принять `max(2, 5 - N)`, где N — число независимых грубых ошибок; после штрафа нужно отдельно определить нижнюю границу. Это расширение вашей шкалы, а не уже принятое правило. Для отсутствующей или непроверяемой работы правило задаётся отдельно.

Нужно выбрать знаменатель среднего: все обязательные работы, только работы с наступившим сроком или только сданные. Последний вариант позволяет получить среднее 5, сдав одну работу из шести. Практичный вариант — показывать текущий средний балл и полноту сдачи отдельно, а итоговый автомат выдавать только после выполнения обязательного набора. Значение за несданную работу и минимальные условия получения автомата необходимо объявить заранее.

Пример согласованной арифметики для полностью сданного набора: оценки `5, 4, 3, 5, 4, 5` дают среднее `26/6`, автомат — 4. Штраф применяется к каждой лабораторной до вычисления среднего; округление вниз выполняется один раз в конце.

### 2. Дата сдачи, исправления и штраф

«Дата коммита диаграммы» неоднозначна: первый коммит с файлом, последняя правка файла или первая версия, заслужившая зачёт? Коммит README не должен менять срок сдачи диаграммы.

Нужно утвердить:

- Полное время дедлайна и часовой пояс, например `2026-11-01T23:59:59+05:00`.
- «Больше трёх дней» — строго больше 72 часов после дедлайна или правило по календарным датам? Ровно на границе штрафа быть не должно, если сохраняем формулировку «больше».
- Для штрафа брать дату первой попытки, текущей версии или первой достаточно качественной версии? Иначе пустой файл до дедлайна может навсегда убрать штраф.
- После улучшения работы оценка пересчитывается? Сохраняется ли штраф? Можно ли понизить оценку за ухудшенную новую версию, удаление файла или найденную позже ошибку?
- Есть ли окончание приёма работ и индивидуальные переносы сроков?

Предложение: хранить историю попыток, дату коммита конкретного артефакта, время первого обнаружения и время проверки отдельно. Рекомендуемый вариант пересдач — разрешать повышение оценки, явно закрепив, какая успешная попытка определяет просрочку. Конкретный порог успешности также нужно выбрать.

Git-даты доступны для изменения автором; коммит, созданный до дедлайна, может быть отправлен на GitHub позже. Если сохраняем ваше правило по коммиту, это осознанное ограничение. Утреннее обнаружение не доказывает точное время публикации. Историю надо получать достаточно глубоко; одного HEAD недостаточно.

### 3. Общая оценка команды и индивидуальный автомат

Нужны устойчивый ID команды, название, ФИО участников, учебная группа, URL репозитория и номер темы. Термины «учебная группа» и «команда/подгруппа» лучше разделить.

Нужно решить, получают ли все участники одинаковые баллы, требуется ли личная защита, как учитывать смену состава, выход участника и команду из четырёх человек. Сейчас запрет на переполнение есть, но порядок исправления и отражения в результатах не описан. Анализ числа коммитов не заменяет оценку личного вклада.

Предложение: проверять один раз на команду, а индивидуальные исключения хранить отдельными решениями преподавателя. Запретить дублирование студента в нескольких активных командах и проверить существование номера темы.

### 4. Сколько лабораторных и что входит в автомат

Из памятки следуют пять диаграмм и приложение с видео. Неясно, приложение — шестая лабораторная, приложение и видео — два этапа или видео является условием сдачи приложения. Нужны точный список, сроки, обязательность и веса. Если все этапы равнозначны, это также стоит прямо записать.

Видео нельзя считать проверенным только по наличию файла, а работоспособность приложения — по наличию `solution/`. Предлагаю на первом этапе автоматизировать диаграммы, для приложения автоматически проверять комплектность, а демонстрацию и окончательную оценку приложения оставлять преподавателю. Если нужна проверка запуска приложения или содержания видео агентом, это отдельный объём реализации с собственными критериями.

## Противоречия и пробелы в учебных требованиях

### Предметная область и выбор темы

[domains.md](domains.md) содержит 11 разделов и 30 подпунктов дорожной карты, а не 11 одинаково устроенных заданий на приложение. Нужно определить: команда выбирает раздел, подпункт или целый маршрут; могут ли темы повторяться; какой минимальный процесс требуется для коротких тем вроде фотографий или ИНН.

В документе встречаются подготовка документов, очные действия и связанные этапы. Для каждой выбранной темы нужно определить границу учебной системы: что делает заявитель, что сотрудник, что считается внешним действием и каким результатом заканчивается услуга. Иначе агент будет додумывать обязательные роли и функции.

Пустые ячейки исходного DOCX сохранены в Markdown как «—»: наследование значения из предыдущей строки не утверждено. Сроки предметных процедур из дорожной карты нельзя смешивать с дедлайнами лабораторных. Документ перенесён без проверки актуальности перечисленных предметных правил.

### Нотации диаграмм

В первой части памятки указаны «классы предметной области», в требованиях к файлам — ER-диаграмма. Это разные представления. Нужно окончательно выбрать `erDiagram` и согласовать формулировки курса либо заменить формат и имя файла.

Диаграмма прецедентов задана через `flowchart`. Нужен небольшой принятый шаблон изображения акторов, вариантов использования и границы системы, чтобы проверять смысл, а не требовать обозначения, которые не оговорены. Обязательность include/extend также нельзя додумывать.

Системная последовательность должна показывать систему как единый объект и внешних участников, внутренняя — взаимодействие компонентов выбранной операции. Лучше потребовать назвать операцию в пояснении и указать её связь с системным сценарием. «Самая большая операция» требует объяснения выбора, иначе агент не сможет воспроизводимо определить её размер.

### Критерии грубых ошибок

Нужна отдельная рубрика для каждого артефакта. Рабочая основа для обсуждения:

| Файл | Возможная грубая ошибка по смыслу | Что нельзя требовать без дополнительных условий |
| --- | --- | --- |
| `use_case.md` | Не показан основной сценарий получения выбранной услуги или обязательный участник процесса | Произвольное число ролей и полный набор административных функций |
| `er.md` | Нет основной сущности заявления/результата либо связи противоречат описанному процессу | Конкретные имена таблиц, одинаковая схема БД у всех команд |
| `system_sequence.md` | Нет основного взаимодействия заявителя с системой, результат процесса не определён | Детали контроллеров, репозиториев и таблиц |
| `class_sequence.md` | Внутреннее взаимодействие выбранной операции отсутствует или не позволяет выполнить её | Определённый архитектурный шаблон без требования курса |
| `classes.md` | Ключевая ответственность отсутствует либо тип отношения меняет смысл модели | Наследование и интерфейсы ради наличия таких стрелок |

Нужно определить, когда отсутствие альтернативных сценариев, кратностей, атрибутов, методов и пояснений становится грубой ошибкой. Одна первопричина должна считаться один раз в одной работе, даже если она описана несколькими замечаниями. Каждая грубая ошибка должна содержать критерий, конкретное место и объяснение нарушения. Мелкие замечания балл не снижают.

### Согласованность по мере семестра

Раннюю диаграмму нельзя штрафовать за отсутствие ещё не назначенной диаграммы или будущего приложения. Нужен поэтапный набор доступных требований. Для поздних этапов агент должен видеть связанные диаграммы и пояснения, а при проверке реализации — нужные исходники.

Следует выбрать, меняется ли оценка ранней лабораторной после изменения другой диаграммы. Предложение: находить междиаграммное противоречие в контексте проверяемого этапа, отдельно публиковать проблему согласованности и не пересчитывать автоматически старую оценку без объявленного правила. Изменение связанных файлов должно инвалидировать кеш зависимой проверки.

## Технический договор для нового «комбайна»

1. Входные Markdown-файлы имеют фиксированные столбцы. Для `labs.md`: ID, название, путь артефакта, тип проверки, срок с часовым поясом, обязательность. Для `groups.md`: ID команды, название, учебная группа, участники, репозиторий, тема; ветка либо задаётся явно, либо используется основная ветка репозитория. При неверной таблице запуск сообщает ошибку, а не молча пропускает строки.
2. Синхронизация фиксирует SHA проверяемого снимка и получает историю файлов. Недоступный репозиторий отмечается как ошибка синхронизации; старый результат остаётся с пометкой о давности. Один сбой не останавливает остальные команды.
3. До AI выполняются проверка расположения файлов, числа Mermaid-блоков, ожидаемого типа диаграммы и проверка синтаксиса выбранным парсером. Парсер, его версия и допустимые особенности Mermaid должны быть едины. Текст после блока также передаётся на содержательную проверку.
4. Подпроцесс Codex получает тему, рубрику, пояснения, нужные связанные артефакты и конкретный SHA. Содержимое репозитория студентов считается проверяемыми данными: инструкции из их README, AGENTS.md и диаграмм не должны управлять проверяющим. На этапе проверки диаграмм агенту не нужны выполнение студенческого кода, секреты и запись в студенческий репозиторий.
5. Модель возвращает структурированный результат: статус, список грубых ошибок с ID критериев и местами, мелкие замечания. Формат валидируется; число ошибок, балл, штраф и среднее считает обычный код. Невалидный ответ и сбой процесса означают техническую ошибку, а не плохую оценку.
6. Для каждой попытки сохраняются ID команды и лабораторной, SHA, хеши входных артефактов и требований, версия рубрики, модель, время коммита и проверки, ошибки, базовый балл, штраф и итог. Markdown-отчёт и сводная таблица строятся из этих данных. Отдельно хранится ручное решение преподавателя с причиной и привязкой к версии.
7. Повторный запуск использует кеш только при совпадении всех значимых входов, включая связанные диаграммы, тему и критерии. Нужна принудительная перепроверка одной лабораторной/команды. Технические сбои повторяются; удаление файла обновляет статус. Смена даты относительно дедлайна должна обновлять сводку даже без вызова AI.
8. У подпроцесса есть таймаут, ограничение повторов и журнал. Результат записывается атомарно после валидации, предыдущая успешная попытка сохраняется. Два утренних запуска одновременно исключаются блокировкой.
9. В `results.md` показываются команда, участники, тема, баллы со ссылками на отчёты, просрочка, полнота сдачи, среднее, автомат и дата обновления. Различаются предварительная оценка AI и подтверждённая преподавателем. При ошибке нового запуска старая оценка явно помечается как результат предыдущей версии.
10. Нужно выбрать место запуска, время и публикацию: ручной запуск утром или планировщик; локальная машина или CI; кто делает commit/push результатов и какие материалы доступны студентам. `run_check.sh` сам по себе не обеспечивает ни расписание, ни доступность отчётов на GitHub. Секреты, кеши репозиториев и технические логи в публичную сводку не входят.

Конкретные параметры запуска Codex здесь намеренно не зафиксированы: перед реализацией нужно проверить установленную версию и её интерфейс. В рамках этого разбора подпроцессы AI, студенческие репозитории и внешние сервисы не запускались.

## Минимальные сценарии приёмки будущей реализации

- 0/1/2 грубых ошибки дают 5/4/3; мелкие замечания не меняют оценку; повторное описание одной ошибки не увеличивает N.
- Проверяются согласованное поведение для 3+ ошибок, отсутствующего файла, неверной нотации и сломанного Mermaid.
- На границе «дедлайн + три дня» штрафа нет; сразу после границы он равен одному баллу, если принята трактовка 72 часов. Изменение README не меняет дату диаграммы.
- Исправление и поздняя пересдача дают результат по утверждённой политике; среднее и округление вниз считаются после штрафов.
- Неизменившиеся входы не вызывают AI; изменение рубрики или зависимой диаграммы запускает нужную перепроверку.
- Таймаут AI, недоступность GitHub и повреждённый ответ не превращаются в студенческий незачёт; следующий запуск повторяет неудавшуюся попытку.
- Удалённая работа не выглядит актуально сданной; ручное решение преподавателя переживает пересборку таблицы.
- Все участники одной команды получают общую оценку по объявленному правилу, индивидуальные исключения видны отдельно.

## Что согласовать в первую очередь

1. Перечень оцениваемых этапов: пять диаграмм плюс приложение? Как учитывается видео?
2. Шкалу для 3+ грубых ошибок и непроверяемых/несданных работ, нижнюю границу после штрафа.
3. Знаменатель среднего и условия выдачи итогового автомата.
4. Дату сдачи для первой попытки и исправлений, часовой пояс, трактовку трёх дней, политику повышения/понижения.
5. Единицу темы из `domains.md` и минимальный объём выбранного процесса.
6. Окончательный выбор ER вместо классов предметной области и рубрики пяти диаграмм.
7. Общую оценку команды, индивидуальные исключения и способ подтверждения преподавателем.
8. Ручной или плановый утренний запуск, место запуска и способ публикации результатов.

После этих решений можно реализовать компактный конвейер по образцу прежнего репозитория. Переносить старые правила автомата, плагиата и защиты зачёта без отдельного решения не следует.
